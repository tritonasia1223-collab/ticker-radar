# 주간 해설 작성·피드백 운영

편집 원칙의 단일 원본은 [인수인계서](../../docs/LIQUIDITY-EDITORIAL-HANDOFF.md)다. 이 문서는 실행 절차다. 초안이 생겼다고 사용자 선호가 확정되거나 모델 가중치가 학습되는 구조가 아니다. 다음 작업자가 갱신된 인수인계서와 사례를 다시 읽고 작성한다.

## 언제, 어디서 실행하나

현재 이 대화에 등록된 예약 작업: **미국 유동성 주간 해설 작성** (ID `automation`). 설정을 바꿀 때 새 작업을 중복 생성하지 말고 이 작업을 갱신한다. CLI는 사본에서 실행돼도 config의 `canonicalRoot`로 기록 위치를 통일한다.

- 기존 GitHub 수집은 그대로 둔다. H.4.1은 한국시간 금요일 07:30, 신용 자료는 화~토요일 10:20에 수집하도록 설정돼 있다. 이는 예약 시각이지 실제 완료 시각이 아니다. GitHub의 예약 트리거 지연을 고려한다.
- 이 대화의 예약 작업은 금요일 11:00 새 주차를 확인하고, 토요일 11:00에 미완료 주차를 재확인한다. GitHub 완료 이벤트에 즉시 연결된 훅이 아니라 수집 이후 준비 상태를 확인하는 방식이다.
- 작업 기준일은 최근 수요일이다. 2026-10-14까지는 기존 작성본으로 처리한다. 같은 주차의 초안이나 사용자 수정본이 있으면 다시 쓰지 않는다. 실패·미완료만 재개한다.
- Codex 로컬 예약은 PC와 앱이 켜져 있어야 한다. 꺼진 동안에도 기존 GitHub 데이터 수집은 별도로 동작한다. 예약 누락 시 수동으로 아래 절차를 실행한다.
- 운영 원본은 `C:\ticker-radar-master`의 이 도구·인수인계·기록이다. 현재 앱 편집 대상은 `.deploy/credit-monitor`이나 작업 시작마다 실제 경로와 Git 상태를 확인한다. 다른 작업의 변경을 초기화하거나 덮어쓰지 않는다.
- 2026-11-19 사용자 직접 지시로 주간 해설의 상시 배포가 허용됐다. 새 주차와 직접 피드백 수정본은 검증 후 바로 배포한다. 이 권한은 주간 해설과 필요한 표시·검증·운영 기록에 한정한다. 배포는 문안 승인이나 인간 피드백을 뜻하지 않는다.

## 새 주차 작성

1. `AGENTS.md`, 인수인계서, 이 문서와 전주 최종 반영 문안을 읽는다. 전주가 아직 검토되지 않은 AI 초안이면 그 사실을 표시하고, 승인된 사실처럼 반복하지 않는다.
2. 저장소 루트에서 `workflow.mjs status`로 작성 여부를 확인한다. 새 주차 작성 전에는 `node tools/liquidity-editorial/recover-collection.mjs`를 실행한다. `ready`일 때만 `node tools/liquidity-editorial/workflow.mjs prepare`로 자료를 고정한다. `collecting`이면 30~60초 간격으로 상태를 확인하고, `needs_attention`이면 로그·원자료 발표·캐시를 조사한다. 15분 내 준비되지 않으면 원인과 미완료 상태를 알린다. 무조건 토요일까지 대기하지 않는다. `already_covered`이면 조용히 종료한다. `already_written`이면 `preview-status.md`를 확인해 적용·검증·운영 배포도 완료됐을 때 조용히 종료한다. 미완료면 저장된 최신 수정본의 적용·검증·배포 중 남은 단계를 재개한다. 작성 완료 상태만으로 종료하지 말고 deployment.json의 revision·해시와 실제 운영 반영을 확인한다. `waiting_for_data`이면 누락을 정상·무변화로 해석하지 않는다. 기존 prepared 입력은 자동 덮어쓰지 않는다.
3. 새 `data/liquidity-editorial/YYYY-MM-DD/inputs.json`을 분석한다. 전주 대비 모든 항목의 변화 목록을 `comparison.md`에 적는다. 주간·4주·13주, 새 관측·동일 관측·결측·표본 교체·과거 수정치를 구분한다. 핵심 지표는 13주를 넘는 장기 맥락도 기록한다: 분석 기간과 선택 이유, 수준·중간 경로, 큰 한 주가 구간에 들어오고 빠진 효과, 기존 장기 판단의 유지·갱신 근거. 6개월·1년·필요 시 수년 등 지표에 맞는 이력을 확인하고, 부족하면 외부 원자료를 보강한다. 기간별 숫자를 본문에 모두 나열하는 과제가 아니다. 준비 검사 통과가 모든 개별 지표의 최신성을 보장하지는 않는다.
4. 방향 전환, 지속되는 악화, 서로 다른 방향 등 핵심 변화는 외부 조사한다. 공식 자료를 우선하고 검색 질문, 출처 URL, 공개일·사건일, 확인한 사실, 남은 가설을 `research.md`에 적는다. 원인 확인 실패를 인정하되 이를 조사 생략 수단으로 쓰지 않는다. 지표 사이 동행만으로 원인을 단정하지 않는다.
5. `draft-template.json`을 별도 `draft-working.json`으로 복사해 모든 블록을 `write`(새 작성), `carry`(유지), `omit`(이번 주 생략)으로 결정한다. 각 이유와 문단을 적는다. `sources`는 조사 출처, 각 블록 `sourceIds`는 연결된 출처 ID다. 주요 변화는 `materialChange: true`로 표시하고 조사 근거 또는 `researchUnresolved`에 구체적 미확인 사유를 남긴다. 새 관측이 없어 유지하는 블록만 `unchangedNote: true`로 표시한다.
6. 가독성을 별도로 읽어본다. 첫 문장은 변화나 판단, 다음 문장은 배경·의미다. 근거 숫자는 기록에 보존하고 본문에는 이해에 필요한 수치만 남긴다. 과도한 명사 축약, 중복 정의, 형식적인 다음 주 예고를 줄인다. 근거 있는 해석은 적극적으로 작성한다.
7. **원본 보존을 먼저** 한다. `node tools/liquidity-editorial/workflow.mjs draft <draft-working.json 경로>`를 실행한다. 인수인계서가 바뀌었다면 다시 읽고 `handoffHash`를 최신 SHA-256으로 갱신한다. 원본과 revision-001은 이후 덮어쓰지 않는다.
8. 이 문안을 해당 주차 앱 코드에 반영하고 로컬 비교 창에서 확인한다. 실제 적용 경로·검증 결과·미리보기 URL을 `preview-status.md`에 남긴다. 주차 이동, 블록 위치, 빨간 유지 안내, 부호·단위·기간을 확인한다. 미리보기 검증을 완료하면 아래 배포 절차를 이어서 실행한다. 이미 초안은 있는데 미완료 단계가 남았다면 다시 작성하지 말고 최신 수정본의 적용·검증·배포만 재개한다.

조사 출처 객체 예: `{"id":"treasury-dts","url":"https://...","title":"자료 제목","claim":"확인한 원인과 범위","accessedAt":"2026-10-23","publishedAt":"2026-10-22","eventDate":"2026-10-21"}`. 현재 주차의 실제 자료를 사용한다. 예제 날짜를 복사하지 않는다.

## 검증 후 바로 배포

1. 저장된 최신 revision과 앱 해설 JSON의 일치를 확인한다. 사용자 수정본을 원본 AI 초안으로 되돌리지 않는다.
2. 최신 origin/master를 가져온 뒤 적합한 깨끗한 배포 작업트리를 재사용하거나 별도 작업트리를 만든다. 작성 작업트리의 무관한 변경을 통째로 옮기지 않는다. 해당 해설·registry·필요한 안내 표시·검사·원본 및 운영 기록만 반영한다.
3. 관련 테스트와 TypeScript·빌드를 통과시킨다. 날짜별 해설과 작은 빨간 안내, 주차 이동을 미리보기에서 확인한다.
4. 검증한 범위만 커밋하고 master에 푸시한다. 원격이 바뀌었으면 최신 변경 위에 반영하며 강제 푸시는 하지 않는다.
5. Vercel Production 성공과 운영 도메인의 새 해설 제공을 모두 확인한 뒤 deployment.json에 실제 revision·해시·커밋·운영 URL·확인 시각을 기록한다. 실패를 완료로 쓰지 않는다. 다음 실행은 이 기록으로 중복 배포를 막는다.
6. 배포 완료를 사용자에게 알린다. 이후 사용자가 운영 화면을 보고 주는 직접 피드백은 기존 기록 절차로 처리하고 수정본도 검증 후 배포한다. 운영 배포 자체를 문안의 인간 승인으로 기록하지 않는다.

## 사용자가 직접 피드백했을 때

예약 실행은 피드백을 만들어내지 않는다. **실제 사용자가 이 대화 등에서 한 수정·삭제·추가·확정 요청이 출발점**이다. 무응답, 초안 자체, 다른 에이전트의 제안, 변경 지시가 없었다는 사실을 승인이나 선호로 기록하지 않는다. 사용자는 별도의 학습 명령을 줄 필요가 없다.

1. 사용자가 지정한 주차·블록만 고친다. 문구 제안을 요청했을 뿐이면 제안을 보여주고, 확정하지 않은 문안을 적용 완료로 기록하지 않는다.
2. 피드백 원문, 근거 대화, 수정 전후, 변경 이유와 적용 범위를 남긴다. 문체/일회성/지표/데이터 계산을 구분한다. 단순 수치·오타 수정에서 새 문체 규칙을 발명하지 않는다.
3. 최신 revision 전체를 복사해 `after`를 만들고 아래 JSON을 작성한다. `node tools/liquidity-editorial/workflow.mjs feedback <파일>`로 원본을 보존하며 새 revision·피드백·인수인계 이력을 함께 저장한다. `source.kind=human`은 증빙 입력 요건이지 사용자 인증 장치가 아니다. 실행자는 실제 인간 메시지를 확인해야 한다.
4. 새로운 공통 원칙이 있으면 인수인계서의 해당 본문에도 통합한다. 기존 규칙과 같으면 사례만 추가하고 규칙을 복제하지 않는다. 이전 규칙을 대체하면 변경 이유와 과거 범위를 남긴다. CLI가 추가한 이력 표식과 원문 기록은 보존한다. 새 원칙이 없으면 `lessons: []`로 주차 문안 수정만 기록한다.
5. 앱 반영·로컬 확인을 완료한 뒤 어떤 문구와 작성 기준을 고쳤는지 짧게 알린다. 해당 수정본도 검증 후 바로 배포한다. 완료를 보고하기 전에 인수인계 갱신과 운영 반영 확인까지 끝낸다.

```json
{
  "id": "human-YYYYMMDD-001",
  "asOf": "YYYY-MM-DD",
  "baseRevision": 1,
  "handoffHash": "수정 전 인수인계서 SHA-256",
  "source": {"kind":"human", "quote":"사용자가 직접 한 말", "reference":"대화 ID 또는 날짜·메시지를 찾을 수 있는 설명"},
  "after": {"설명":"최신 revision과 동일한 전체 초안 구조, 지정한 부분만 수정"},
  "lessons": [{"scope":"week", "kind":"one_off", "text":"이 주차에서만 삭제. 다음 관측 발표 시 재검토."}]
}
```

범위는 `week / indicator / general / data`, 상태는 `explicit / inferred / one_off / correction`이다. 추론을 명시 지시로 승격하지 않는다. 사용자 의도가 명확하면 이미 승인한 편집을 재승인받지 않는다.

2026-10-14 이전 주차에 새 피드백이 오면 실제 반영 문안을 먼저 같은 초안 형식으로 전사하여 `node tools/liquidity-editorial/workflow.mjs adopt <파일>`로 기준본을 등록한다. 이 기준본은 최초 AI 초안이 아니다. `provenance.md`와 기존 복구 원본을 함께 보존한 뒤 feedback을 실행한다.

## 보존·복구·점검

`recover-collection.mjs`는 이번 주 수요일 H.4.1 행과 당일(한국시간) 신용 수집 시각, GitHub 실행 상태를 함께 검사한다. 실행 중이면 중복 요청하지 않는다. 필요한 자료가 없으면 기존 수집을 직접 실행하되 워크플로별 하루 한 번만 복구 요청한다. 응답이 유실돼도 요청 기록을 남겨 반복 실행을 막는다. 성공 직후 API가 오래됐으면 10분간 게시·캐시 지연으로 구분하며, 계속 오래되면 원자료와 서버를 조사한다. 성공 표시만으로 최신화 완료라 하지 않는다. 권한·네트워크 오류는 보고하고 자료 결측과 구분한다.

복구 기록은 `data/liquidity-editorial/collection-recovery`에 저장한다. 이 절차는 11시 로컬 예약에 연결되어 있어 PC·앱 실행이 필요하다. GitHub 자체가 정시에 시작한다고 보장하는 변경은 아니다. 기존 서버 수집 예약은 유지한다. 복구 검사는 `node --test tools/liquidity-editorial/recover-collection.test.mjs tools/liquidity-editorial/workflow.test.mjs`로 실행한다.

- `inputs.json`, `handoff-at-prepare.md`: 작성 당시 데이터·기준. 공개 API 자료만 보관한다.
- `draft-original.json/.md`, `handoff-at-draft.md`: 최초 초안과 실제 사용 기준.
- `revision-NNN.json/.md`, `feedback-ID.json`: 수정본, 사용자 발언, 전후 문안. 자동 덮어쓰기 금지.
- `state.json`: prepared → awaiting_feedback → human_revised. 사용자 수정 상태이지 사실 검증이나 배포 승인 표시가 아니다.
- `comparison.md`, `research.md`, `preview-status.md`: 분석 범위, 외부 조사, 적용·검증 결과.
- `deployment.json`: 실제 배포한 주차·revision·해설 해시·커밋·운영 URL·확인 시각. 작성/사용자 수정 상태와 별개다.
- 최신 상태는 `node tools/liquidity-editorial/workflow.mjs status`, 저장 검증은 `node --test tools/liquidity-editorial/workflow.test.mjs`.
- 중간 실패는 같은 피드백 ID와 같은 입력으로 재시도한다. 충돌 시 최신 상태와 원문을 확인해 병합하며, 원본이나 잠금을 강제로 지워 해결하지 않는다. 잠금 파일에는 프로세스 번호가 있으므로 실제 실행 여부부터 확인한다.
- 네트워크/게시 지연은 다음 실행에서 재확인한다. 이미 작성한 주차의 사후 데이터 수정은 자동 재작성하지 말고 영향 범위를 보고한다. 여러 주차 누락 시 미작성 기준일을 확인해 과거→최근 순서로 `prepare YYYY-MM-DD`를 수동 실행한다.
- 운영 원본은 로컬에 보존하고 주간 해설 배포 시 해당 주차 원본·피드백·인수인계도 함께 변경 목록에서 검토한다. 무관한 작업을 일괄 커밋하지 않는다.

## 다음 주에 얼마나 나아졌는가

사용자 피드백 뒤에는 해당 주차 `review-summary.md`에 유지/추가/삭제/수치 정정, 사용자가 대신 찾아준 외부 원인, 반복된 가독성 수정, 다음 주 적용할 행동을 간단히 정리한다. 수정 횟수를 줄이려고 해설을 비워두는 방식은 개선으로 보지 않는다. 빈 초안보다 근거 있는 적극적인 초안을 선호한다는 지시는 유지한다.
