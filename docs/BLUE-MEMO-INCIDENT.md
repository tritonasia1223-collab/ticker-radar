# 파란 첨삭 메모 저장 누락 점검 (2026-09-15)

상태: 로컬 수정·검증 완료. 2026-09-15 사용자 요청에 따라 운영 배포 진행.

## 확인된 원인

`a0580a5`는 화면·DTO·일반 저장 함수·DB 컬럼에 `refBlue`를 추가했지만, 현재 경제사 화면이 사용하는 협업 저장 경로에는 반영하지 않았다.

1. `Capitalism.onEditContent`가 캐시에 파란 메모를 반영한다.
2. `saveFlowDraft`의 `flowDocument`가 `refBlue`를 누락한다.
3. 파란 메모만 수정한 경우 변경분이 `[]`가 되어 저장 요청 및 기기 초안이 생성되지 않는다.
4. 다른 수정의 저장 응답이나 동기화로 문서를 다시 구성하면 화면의 파란 메모도 빠진다.

서버 협업 경로도 허용 필드·Zod 노드 스키마·DB 쓰기 데이터에서 `refBlue`가 누락되어 있었다. 일반 POST/PATCH 입력 스키마도 미반영 상태였으나, 현재 그 HTTP 쓰기 경로는 협업 프로토콜 전환 가드로 차단되어 있다.

## 복구 조사

사용자 제보: 점검 약 20~30분 전부터 2024년 이후 여러 카드에 메모 추가 후 소실.

읽기 전용 DB 점검에서 현재 비어 있지 않은 파란 메모 0개, `refBlue`를 포함한 협업 저장 이력 0개, 파란 메모 내용이 있는 카드 버전 0개였다. 로컬에는 당일 롤링 백업 파일도 없었다. 서버 삭제를 입증한 것이 아니라, 서버 저장 전에 내용이 누락되는 코드 경로를 재현했다. 작성 PC의 브라우저 메모리/입력칸/복사본은 별도 확인 대상이다.

조사 결과는 Git에서 제외되는 `script/cap-export/ref-blue-audit.json`에 보존했다. 운영 데이터를 변경하거나 전체 카드를 복원하지 않았다.

## 수정 및 검증

- 협업 문서 직렬화·허용 필드·검증·DB 저장·이력 표시명에 `refBlue` 추가.
- 수정한 클라이언트는 `schemaVersion: 2`를 보낸다. 이전 창이 새 서버 문서를 받아 재직렬화하면서 파란 메모를 암묵적으로 null로 바꾸면 거부하고, 입력을 복사한 뒤 새로고침하도록 안내한다.
- 일반 입력 스키마와 백업 검색·버전 복원 매핑 보완. 직접 전체 저장 함수의 기존 노드에서 필드 생략은 보존, 명시적 null은 삭제로 구분한다.
- 수정 전 실패하던 직렬화 및 서버 필드 검증 테스트 2개를 재현한 뒤 수정했다. 전체 99개 테스트, 타입 검사, 빌드 통과.
- 격리 DB 스키마에서 파란 메모 저장·재조회, 노란 메모와의 동시 병합, 같은 파란 메모 충돌, 파란 메모만 삭제 시 노란 메모 보존을 검증했다. 테스트 스키마만 제거했다.
- 저장 누락 점검에서는 기존 `CapFlow.tsx`의 로컬 여백 수정을 유지했다. 후속 요청으로 표·노란 메모·파란 메모 아이콘을 본문 아래 별도 행에 배치하고, 메모의 기본 autoFocus를 `focus({ preventScroll: true })`로 교체했다.
- 실제 FlowColumn 컴포넌트와 가상 긴 카드로 브라우저 검증: 100%·125% 확대에서 아이콘/본문 비겹침, 노란·파란 메모 생성 시 가로·세로·창 스크롤 좌표 유지(중간 점프 없음), 입력 포커스 및 완료 저장을 확인했다. 테스트 UI의 API는 가로채 운영 연구 데이터를 쓰지 않았다.

운영 반영 후에는 두 사람 모두 현재 입력을 별도로 보관한 뒤 최신 화면을 다시 열어야 한다. 배포 전 운영의 파란 메모 저장 문제는 그대로 남아 있다.
