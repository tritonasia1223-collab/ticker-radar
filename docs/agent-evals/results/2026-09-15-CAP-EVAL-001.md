실험일: 2026년 9월 15일(한국 표준시)

## 실험 목적

Claude와 Codex가 실제 코딩 에이전트 환경에서 구현과 검증을 담당할 때 성능, 비용, 소요 시간이 어떻게 달라지는지 비교한다. 저장소, 기준 커밋, 구현 과제, 완료 조건, 검증 프롬프트와 객관 검사를 동일하게 유지하고 실행 주체만 교차했다.

평가 과제는 자본주의 경제사 타임라인에 기존 노란 메모와 파란 첨삭 메모에 이어 독립적인 세 번째 `보라색 해석 메모`를 추가하는 것이었다. UI뿐 아니라 클라이언트 직렬화, REST 검증, 서버 CRUD, Drizzle 스키마, 협업 diff·병합, 구버전 클라이언트 보호와 자동화 테스트까지 구현 범위에 포함했다. 운영 데이터, 운영 DB, 실제 배포는 실험에서 제외했다.

## 구현 결과 최종 판정

### 유효한 결함

1. **P1, 두 후보 공통: 구버전 초안을 복구하면 저장된 보라색 메모가 삭제될 수 있다.** 버전 2 화면은 `refPurple`을 직렬화하지 않는다. 이 화면의 저장 요청은 거절되지만 로컬 초안은 남는다. 최신 버전으로 새로고침한 뒤 초안을 복구하면, 누락된 필드를 버전 3의 명시적인 `기존 값 → null` 삭제 요청으로 해석한다. 서버는 이 요청을 정상 요청으로 받아 병합한다. 실제 직렬화기, 복구 엔진, 서버 검증기와 병합 함수를 사용해 데이터 손실을 재현했다.
2. **P2, Claude 후보만 해당: 도구 버튼으로 기존 보라색 메모의 편집기를 열 수 없다.** 버튼은 `autoEdit` 값을 변경하지만 `MemoCard`의 편집 상태는 최초 마운트 때만 이 값을 읽는다. 이후 값 변경을 반영하지 않기 때문에 버튼을 눌러도 편집기가 열리지 않았다. Chrome에서 두 번 재현했다. 메모 본문을 직접 클릭하면 편집기는 열린다.
3. **낮음, Codex 후보만 해당: 격리 UI 테스트가 최초 실행에서 간헐적으로 실패한다.** Vite의 의존성 최적화가 첫 실행 중 페이지를 다시 불러오면서 테스트 전역 객체가 사라졌다. 다시 실행하면 네 가지 화면 조합이 모두 통과했다. 제품 결함보다는 테스트 인프라의 불안정성에 해당한다.

DB 마이그레이션을 서버 배포보다 먼저 실행해야 한다는 점은 실제 운영 전제 조건이다. 다만 배포가 과제 범위에서 제외되었고 두 후보 모두 DDL과 관련 문서를 만들었으므로 구현 결함으로 계산하지 않았다. 색상 메모가 내보내기와 무결성 검사에서 빠지는 기존 문제도 이번 기능의 구현 결함으로 계산하지 않았다.

## 검증자 성능 비교

최종 판정에서 인정한 중요 결함 사례는 세 건이다. 두 후보에 각각 존재하는 공통 P1 두 건과 Claude 후보에만 존재하는 P2 한 건이다.

Codex 검증자는 세 건을 모두 찾아 직접 재현했다. Claude 검증자는 세 건 모두 찾지 못했고, Claude 후보에는 통과, Codex 후보에는 판정 보류를 내렸다. Claude도 낮은 우선순위의 운영·테스트 공백을 일부 찾았지만 핵심 회귀 문제를 찾아내지는 못했다.

이번 과제에서 가장 큰 추가 가치를 만든 조합은 **Claude 구현을 Codex가 검증한 경우**였다. 잘못된 통과 판정을 뒤집고 두 가지 중요 결함을 모두 찾아냈다. Codex 자체 검증도 공통 P1을 찾았다. Claude 검증은 두 후보의 배포 판단을 실질적으로 개선하지 못했다.

다만 이번 결과는 의도적으로 까다롭게 만든 하나의 합성 과제에서 나온 값이다. 이 프로젝트와 이번 작업 방식에서 관찰한 결과로 보아야 하며, 모델 전체의 일반적인 우열을 확정하는 자료로 사용할 수는 없다.

다음 실행 전 객관 검사에 아래 두 회귀 시나리오를 추가해야 한다.

1. 구버전 화면에 남은 초안을 최신 화면에서 복구해도 새 필드가 삭제되지 않는지 검사한다.

## 결론 및 운영 추천안

이번 한 건의 결과만 놓고 보면 **Codex가 구현하고 Codex가 독립 검증하는 흐름**을 기본값으로 삼는 것이 가장 합리적이다. 네 조합 중 API 환산 비용이 가장 낮았고, 구현 품질도 상대적으로 나았으며, 자체 검증에서 실제 데이터 손실 결함을 찾아냈다. 다만 같은 모델의 자기 검증이 언제나 충분하다는 뜻은 아니다. 이번 결과를 기본 운영안으로 사용하면서 과제를 누적해 다시 판단해야 한다.

Claude는 구현 대안이 필요한 과제에 선택적으로 투입하는 편이 좋다. 복잡한 UI 설계나 서로 다른 구현 접근을 비교할 가치가 있을 때 Claude 구현 후보를 추가로 만들고, 최종 검증은 Codex가 맡는다. 이번 실험에서 **Claude → Codex**가 Claude 후보의 잘못된 통과 판정을 바로잡았기 때문에, Claude가 구현한 변경을 Claude 자체 검증만으로 배포하는 흐름은 당분간 피하는 것이 좋다.

실제 프로젝트에는 작업 위험도에 따라 다음과 같이 적용하는 것을 권한다.

1. **낮은 위험 작업**: 한 모델이 구현하고 타입 검사·단위 테스트·빌드 같은 객관 검사만 수행한다. 문구, 스타일, 단순 배치처럼 저장 데이터와 무관한 변경이 여기에 해당한다.
2. **중간 위험 작업**: 구현과 별도의 새 세션에서 Codex 검증을 필수로 실행한다. 기존 데이터 구조를 읽고 쓰거나 여러 화면에 영향을 주는 기능이 여기에 해당한다.
3. **높은 위험 작업**: Codex 독립 검증에 실제 DB·브라우저 통합 테스트를 함께 실행한다. 협업 저장, 동시 편집, 마이그레이션, 복구, 백업·복원처럼 데이터 손실 가능성이 있는 변경이 여기에 해당한다. 필요하면 Claude 구현 후보를 추가해 두 접근을 비교하되, 두 후보를 모두 배포하지 않고 검증을 통과한 한쪽만 선택한다.

검증 프롬프트에는 “기능이 보이는가”보다 **저장 후 재조회되는가, 구버전과 최신 버전이 섞여도 보존되는가, 두 창이 동시에 수정해도 다른 필드가 사라지지 않는가**를 완료 조건으로 명시해야 한다. 에이전트가 검증했다고 보고하는 것만으로 통과시키지 말고, 각 조건에 대응하는 실행 명령, 브라우저 재현 또는 DB 조회 결과를 증거로 남겨야 한다.

비용 측면에서는 현재 구독 환경에서 Codex의 실제 추가 결제가 없으므로 Codex 독립 검증을 생략할 이유가 적다. Anthropic API는 구현과 검증을 모두 Fable 5.1로 실행하면 비용이 빠르게 증가하므로, Claude는 모든 작업의 상시 검증자보다 대체 구현자 또는 특정 고난도 과제의 보조 검토자로 사용하는 편이 효율적이다.

최종 운영 결론은 다음과 같다.

- 기본 파이프라인은 **Codex 구현 → 객관 검사 → 새 Codex 세션의 독립 검증**으로 둔다.
- Claude가 구현한 작업도 최종 검증은 Codex가 맡는다.
- DB·협업·복구 기능은 실제 PostgreSQL과 브라우저를 연결한 통합 테스트가 없으면 배포 가능 판정을 내리지 않는다.
- 다음 5~10개의 서로 다른 과제에서 같은 방식으로 품질·시간·비용을 누적한 뒤 모델 역할을 다시 조정한다.
- 이번에 발견한 두 회귀 시나리오는 이후 모든 메모·협업 기능의 고정 테스트로 편입한다.

이 방식은 에이전트 숫자를 늘리는 것보다 검증 역할을 분리하고, 실제 데이터 경로를 객관적으로 재현하는 데 초점을 둔다. 이번 파란 메모 사례처럼 화면에서 기능이 만들어지는 것과 저장·복구까지 안전하게 동작하는 것은 별개의 완료 조건이기 때문이다.
