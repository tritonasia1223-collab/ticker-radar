# 경제사 협업 편집 — 2026-09-09

2명이 여러 창에서 편집할 때의 내용 손실을 줄이는 업데이트입니다. 자본주의 경제사의 사건 카드·노드·사건 인사이트·메타 카드를 대상으로 합니다. 보류 중인 종목 기능과 기존 보안·인증 정책은 변경하지 않습니다.

## 사용법

1. 배포 뒤 기존 창은 작성 중인 내용을 별도 보관하고 새로고침합니다. 구버전 창의 저장은 428로 거절됩니다.
2. 상단 **내 이름**을 각자 설정합니다. 다른 편집자의 이름과 최근 편집 카드가 표시됩니다. 표시 이름은 인증 계정이 아닙니다.
3. 본문·메모·표·제목·인사이트는 자동 저장됩니다. 날짜·기간은 날짜 패널의 **저장** 버튼으로 확정하고, 표 너비는 드래그를 끝내야 저장됩니다.
4. 다른 칸이나 다른 필드는 자동 병합됩니다. 같은 필드의 충돌은 양쪽 내용을 비교해 **서버 내용 / 내 내용 → 선택한 내용 반영**으로 처리합니다. 충돌 중에는 편집을 잠시 멈추고 기기 초안을 유지합니다. 양쪽 문장을 섞으려면 먼저 필요한 내용을 복사한 뒤 선택·저장을 마치고 편집합니다.
5. 저장 실패는 **저장 다시 시도**를 누릅니다. 새로고침 후 남은 초안은 **서버와 비교해 복구**를 누릅니다. 서버와 같은 요청 ID를 재사용해 응답만 유실된 저장을 중복 적용하지 않습니다.
6. **변경 이력**에서 수정자·시간·이전/이후 값을 확인하고 **이 변경만 되돌리기**를 사용할 수 있습니다. 이후 다른 사람이 같은 부분을 바꾸었으면 다시 충돌 비교를 거칩니다. 삭제된 카드의 이력도 조회 가능합니다.

## 병합 단위

| 동시에 편집한 내용 | 처리 |
|---|---|
| 다른 사건·다른 노드 | 각 변경 보존 |
| 같은 노드의 본문 / 메모 / 표 | 서로 다른 필드는 병합 |
| 같은 카드의 제목 / 노드 / 사건 인사이트 | 서로 다른 필드는 병합 |
| 다른 메타 카드, 같은 메타 카드의 제목 / 본문 | 변경 필드 병합 |
| 같은 본문, 같은 표, 같은 사건 인사이트, 같은 메타 본문 블록 배열 | 충돌 시 사용자 선택. 글자·셀 단위 실시간 공동 편집은 아님 |
| 독립적인 노드 추가·삭제 | 안정적인 노드 키를 기준으로 병합 |
| 같은 항목 삭제와 수정, 서로 다른 순서 재배치 | 충돌 확인 |

서버가 트랜잭션 잠금 안에서 최신 문서의 필드 값을 검사합니다. 충돌이 하나라도 있으면 요청 전체를 거절하고 연구 데이터와 이력을 모두 변경하지 않습니다. 성공 시 변경한 행과 실제 변경 이력을 함께 기록합니다. 기존 노드 ID는 유지합니다. 전체 카드/메타 배열을 마지막 요청으로 덮어쓰는 저장 경로는 브라우저에서 막았습니다.

클라이언트는 카드별 요청을 직렬화합니다. 진행 중 요청의 ID와 내용을 고정하고, 응답을 기다리는 동안의 추가 입력은 응답의 최신 문서에 다시 적용합니다. 기기 초안에는 비교 기준·작성본·전송 요청을 함께 보관합니다. IndexedDB 기록 실패는 별도로 알립니다.

## 운영과 한계

- 다른 창의 변경은 약 5초마다 확인합니다. 접속 표시 갱신은 15초, 만료는 45초입니다. 접속 표시는 강제 편집 잠금이 아닙니다.
- 기기 저장소 삭제, 비공개 창 종료, 디스크 오류 뒤의 미저장 초안 복구까지 보장하지 않습니다. 서버 저장 완료 여부를 확인하고 기존 전체 백업도 유지합니다.
- 전역 화살표는 기존 개별 추가/삭제 API를 유지합니다. 위험했던 전체 링크 스냅샷 Undo는 화면에서 제외했습니다. 본문·표·카드 협업 이력에 화살표 편집은 포함되지 않습니다.
- 새 이력은 업데이트 이후 성공한 저장부터 기록됩니다. 이전 `cap_history` 스냅샷 및 로컬 백업은 보존하며 기존 CLI로 조회합니다. 기존 관리 스크립트의 직접 DB 쓰기는 협업 잠금을 우회하므로 공동 편집 중 실행하지 않습니다.
- 요청 ID 중복 방지를 위해 `cap_edit_operations`를 자동 삭제하지 않습니다. 이미지가 포함된 필드의 변경 이력은 용량이 커질 수 있습니다. 이력 정리 정책은 추후 별도로 설계합니다.
- 운영 반영 순서: `cap:backup` → 검증 → `cap:collab:init`(테이블 2개 추가만) → 배포 → `cap:integrity` 및 읽기 확인. 공유 Supabase에 `drizzle-kit push`를 사용하지 않습니다.
