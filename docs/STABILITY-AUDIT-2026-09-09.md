## 발견 사항

### F01 · P1 — 편집 중 새로고침하면 경고 없이 초안이 사라짐

위치: [CapFlow.tsx:121](../client/src/components/CapFlow.tsx:121), [Capitalism.tsx:615](../client/src/pages/Capitalism.tsx:615).

노드 입력은 `setDraft`로 컴포넌트 안에만 보관하며, `onBlur`에서 부모 저장기로 넘어간다. 이탈 경고는 `patchBufRef`에 들어간 편집만 검사한다. 따라서 아직 입력창을 벗어나지 않은 초안은 경고 대상에서도 빠진다.

재현: 기존 노드에 `Unblurred draft` 입력 → 1초 대기 → 포커스를 옮기지 않고 새로고침. 저장 요청은 0건이었고, beforeunload 이벤트도 취소되지 않았으며, 다시 열린 화면에는 원래 본문만 남았다. 인사이트·메타 본문 역시 입력 중 로컬 상태와 blur 저장을 나누는 구조라 같은 이탈 정책을 함께 정리해야 한다.

수정 방향: 입력 중 초안, 전송 대기, 전송 중, 저장 실패를 모두 추적한다. 초안을 로컬에 복구 가능한 형태로 남기고, 미저장 내용이 있을 때 이탈 경고를 적용한다. blur는 저장을 앞당기는 계기로 사용할 수 있지만 유일한 초안 보호 수단으로 두지 않는다.

### F02 · P1 — 저장 중 창 포커스 복귀 후 다른 편집을 하면 본문이 되돌아가 저장됨

위치: [Capitalism.tsx:579](../client/src/pages/Capitalism.tsx:579), [Capitalism.tsx:414](../client/src/pages/Capitalism.tsx:414), [Capitalism.tsx:633](../client/src/pages/Capitalism.tsx:633).

PATCH를 보내는 순간 버퍼에서 항목을 지우기 때문에, 요청이 아직 처리 중이어도 포커스 핸들러는 저장 대기가 없다고 판단한다. 이때 재조회한 예전 서버 본문이 낙관적 캐시를 덮는다. 나중에 PATCH 응답이 오면 본문은 그대로 두고 버전만 최신으로 바꾼다. 그 결과 **예전 본문 + 최신 버전**이라는 잘못된 조합이 만들어진다.

재현: PATCH에 2.2초 지연 → 본문 편집·blur → 요청 중 focus 이벤트 → 화면이 원래 본문으로 회귀. PATCH 완료 후 서버에는 새 본문, 화면에는 옛 본문이 남았다. 이어 제목을 바꾸자 버전 검사를 통과한 전체 저장이 옛 본문을 서버에 다시 덮었다. 다른 사용자나 다른 탭의 동시 편집이 없어도 재현됐다.

수정 방향: 카드별 진행 중 요청과 실패한 변경까지 추적하고, 미저장 변경이 있는 카드에 대한 재조회 덮어쓰기를 막는다. 응답 버전은 해당 응답의 상태와 연결해서 관리해야 한다. 버전 숫자만 올리는 처리로는 낙관적 캐시와 서버의 일치를 보장할 수 없다.

### F03 · P1 — 메타 카드 연속 저장이 역순 처리되면 최신 내용이 사라짐

위치: [Capitalism.tsx:60](../client/src/pages/Capitalism.tsx:60), [capitalism.ts:404](../server/capitalism.ts:404).

메타 카드는 전체 카드 배열을 직렬화해 매번 독립 PUT으로 보낸다. 일반 사건의 저장 큐와 버전 검사를 사용하지 않으며, 서버도 키 하나의 값을 그대로 교체한다. 앞선 요청이 늦게 도착하면 최신 저장을 이전 배열로 덮을 수 있다. 이 경로는 사건 카드의 version-on-write 히스토리에도 포함되지 않는다.

재현: 제목을 `Meta older`로 저장한 요청을 지연 → `Meta newest`로 다시 저장 → 앞선 요청 도착. 화면은 `Meta newest`, 테스트 API의 최종 저장값은 `Meta older`였다.

수정 방향: 메타 카드도 저장 순서와 버전을 관리한다. 우선 설정 키별 큐와 실패 상태를 추가하고, 이후 카드별 저장으로 좁히면 카드가 많아질 때 전체 배열 교체도 줄일 수 있다. 메타 카드 복구 이력도 사건 카드와 같은 수준으로 마련한다.

### F04 · P1 — 구조 되돌리기가 이후의 본문·인사이트 수정까지 취소함

위치: [capitalism-undo.ts:53](../client/src/lib/capitalism-undo.ts:53), [capitalism-undo.ts:73](../client/src/lib/capitalism-undo.ts:73).

Undo는 삭제한 노드 등의 변화만 되돌리는 대신, 당시 카드 전체 스냅샷을 다시 저장한다. 서버에 새로 생긴 노드는 보존하지만, 원래 있던 노드의 최신 텍스트·표·메모와 카드 인사이트는 스냅샷 값으로 돌아간다. 이 POST에는 baseVersion도 없다. 일반 카드 저장 큐와도 별개로 실행된다.

재현: A/B 노드가 있는 카드에서 A 삭제 → B 본문과 인사이트 수정 → A 삭제 되돌리기. 실제 `applyUndo` 호출 결과 B는 `B old`, 인사이트는 `Insight old`로 돌아갔다. 텍스트 편집은 구조 Undo 스택에서 제외되어 있으므로, 사용자가 마지막 구조 변경만 되돌리려 해도 그 뒤의 텍스트가 함께 사라진다.

수정 방향: Undo 항목을 변화 단위로 기록한다. 노드 삭제 Undo는 해당 노드와 필요한 연결만 복원하고, 무관한 현재 텍스트·인사이트는 유지한다. Undo도 일반 저장 큐와 버전 검사 안에서 처리해야 한다.

### F05 · P2 — 마지막 노드 삭제가 별도 인사이트까지 삭제함

위치: [CapFlow.tsx:195](../client/src/components/CapFlow.tsx:195), [Capitalism.tsx:528](../client/src/pages/Capitalism.tsx:528), [capitalism-flowops.ts:100](../client/src/lib/capitalism-flowops.ts:100).

화면의 버튼은 ‘이 칸 삭제’지만, 남는 노드가 없으면 카드 자체를 삭제한다. 카드에 인사이트·표·이미지 블록이 남아 있는지는 확인하지 않는다. 서버의 카드 삭제는 관련 노드·엣지·카드 간 링크도 정리한다.

재현: 인사이트가 있는 카드와 빈 노드 배열을 실제 `persistNodes`에 전달하면 인사이트를 보존하는 저장이 아니라 카드 DELETE가 발생했다. 기존 기록 복구 장치가 있더라도 작은 UI 동작의 삭제 범위가 표시보다 넓다.

수정 방향: 마지막 노드를 지워도 별도 인사이트가 있는 카드는 보존한다. 카드 전체 삭제가 필요하면 칸 삭제와 구별되는 명시적 동작으로 제공한다.

### F06 · P2 — 결측 기간을 압축하여 ‘월간·13주’ 계산이 달라짐

위치: [fed.ts:266](../server/fed.ts:266), [fed.ts:272](../server/fed.ts:272), [Fed.tsx:542](../client/src/pages/Fed.tsx:542), [Fed.tsx:744](../client/src/pages/Fed.tsx:744).

재무부 월간 데이터는 종류 하나라도 빠지면 그 달을 배열에서 제거한다. 다음 달 순발행은 직전 달인지 확인하지 않고 마지막으로 남은 행과 차감한다. 12개월 합산도 마지막 12행을 사용한다. 주간 데이터 역시 불완전주를 건너뛰는데, 화면의 13주 계산은 13행 전 값을 사용한다.

재현: Bills 잔액을 1월 100, 2월 200, 3월 300으로 만들고 2월의 다른 국채 종류 하나를 제거했다. 실제 `buildTreasury`는 2월을 건너뛰고 3월 Bills 순발행을 100이 아닌 200으로 반환했다.

수정 방향: 달력 기준 간격을 보존하고 결측은 null/불완전 상태로 유지한다. 월간 증감은 전월이 완전할 때만, 13주 비교는 실제 날짜 간격에 맞춰 계산한다. 운영 DB에 현재 결측이 있다는 뜻은 아니며, 수집 일부 실패 시 잘못된 결과를 만들 수 있는 경로를 확인한 것이다.

### F07 · P2 — 수집 누락을 긴급대출 0으로 바꿔 ‘평상시’처럼 표시할 수 있음

위치: [fed.ts:164](../server/fed.ts:164), [fed.ts:188](../server/fed.ts:188), [Fed.tsx:735](../client/src/pages/Fed.tsx:735).

optionalZero는 프로그램 비활성기의 결측을 0으로 취급하려는 목적이지만, 프로그램이 존재하는 기간의 수집 누락까지 같은 방식으로 처리한다. 현재 로직에는 둘을 구별할 관측 상태가 없다. 핵심 부채가 있으면 해당 주는 화면에 포함되므로 긴급대출 누락이 숨겨질 수 있다.

재현: 핵심 자산·부채만 있고 대출 관측은 하나도 없는 주를 실제 `buildWeekly`에 전달하면 그 주가 포함되고 `loans: 0`을 반환했다. 화면은 이 값을 그대로 위기 판단 임계값과 비교한다.

수정 방향: ‘관측된 0’, ‘프로그램 시작 전’, ‘수집 누락’을 구분한다. 대출 계열이 불완전하면 위기 감지기에 데이터 불완전을 표시한다. 수집 이후 검증도 최신 관측의 완전성과 지연을 별도 확인해야 한다.

### F08 · P2 — 손실 무결성 검사가 FAIL을 출력하고도 성공 종료함

위치: [cap-integrity-check.ts:43](../script/cap-integrity-check.ts:43), [cap-integrity-check.ts:70](../script/cap-integrity-check.ts:70).

정적 코드 확인 사항이다. lossGuard는 손실을 발견해도 로그만 남기고, 호출부는 항상 `process.exit(0)`으로 끝난다. 다른 작업이 이 스크립트의 종료 코드를 통과 기준으로 사용하면 손실이 있어도 성공으로 판단한다. 현재 GitHub Actions에 이 검사가 연결되어 있다는 뜻은 아니다.

수정 방향: 손실 검사가 결과를 반환하거나 예외를 발생시키고, 실제 손실이면 비정상 종료하게 한다. 백업 부재는 손실 없음과 다른 결과로 표시한다. 의도한 삭제를 검증할 때는 해당 삭제를 허용하는 기준을 명시한다.

### F09 · P2 — API 실패를 ‘데이터 없음’으로 표시하고 재시도 수단이 없음

위치: [Fed.tsx:711](../client/src/pages/Fed.tsx:711), [Fed.tsx:731](../client/src/pages/Fed.tsx:731), [queryClient.ts:55](../client/src/lib/queryClient.ts:55).

미국 유동성은 useQuery의 error 상태를 사용하지 않아 서버 오류·연결 실패도 빈 데이터와 동일한 화면으로 처리한다. 경제사 목록·메타 조회에도 오류 상태를 구분하지 않는 경로가 있다. 공통 설정의 자동 재시도와 재진입 갱신도 꺼져 있다.

재현: 미국 유동성 API가 503을 반환했는데 화면에는 ‘데이터가 없습니다.’만 나타났다. 정상 빈 결과와 일시적 연결 장애를 사용자가 구별할 수 없다.

수정 방향: 로딩·오류·정상 빈 결과를 나누고 수동 재시도 버튼을 제공한다. 경제사는 원본을 읽지 못했을 때 빈 배열을 정상 기준으로 삼아 편집하는 일을 막아야 한다. 기존 낙관적 편집 보호를 고려하여 전역 refetch 설정을 한꺼번에 바꾸지는 않는다.

## 구조 평가와 권장 작업 순서

**먼저 경제사 저장 경로를 통합한다.** 컴포넌트의 초안, React Query의 낙관적 캐시, PATCH 디바운스, 카드별 저장 큐, 409 병합, Undo, 메타 설정 PUT이 현재 별도로 움직인다. 큐가 이미 있어도 포커스 재조회·메타·Undo가 큐 밖에서 상태를 바꾸므로 데이터 손실을 막지 못한다. F01~F04를 실패하는 회귀 테스트로 고정한 뒤 공통 저장 상태 관리로 모으는 것이 첫 작업이다.

**그다음 데이터 손실과 계산의 경계를 명확히 한다.** F05의 삭제 범위를 정리하고, F06~F07의 결측·기간 검증과 F08의 실패 종료를 고친다. 경제사 변경 전에는 기존 백업 도구를 사용하되, 복구 가능한 일관된 스냅샷인지도 확인해야 한다. 현재 목록 조회와 백업은 여러 SELECT를 하나의 동일 시점 읽기로 묶지 않아, 편집과 겹치면 다른 버전의 데이터를 함께 읽을 가능성이 있다. 이 부분은 이번에 실DB 경합으로 재현하지 않았으므로 확정 재현 목록과 분리했다.

**동작을 보호한 뒤 큰 파일을 나눈다.** World.tsx에는 지도 투영·확대/이동·무역·분쟁·전력·원전·팹·상세카드·범례가 함께 있다. 세계 현황판 청크는 빌드 결과 약 1.64MB, gzip 약 433KB였다. 모드별 데이터 로더·계산·패널을 분리하면 수정 영향과 초기 파싱 비용을 줄일 수 있다. 경제사 페이지에서는 특히 저장 로직을 UI와 분리한다. 파일이 크다는 이유만으로 전체 앱이나 프레임워크를 교체할 근거는 찾지 못했다.

**검증 대상을 메인 기능으로 옮긴다.** 현재 테스트 include는 블록체인만 지정하고, Vercel buildCommand는 vite build뿐이다. 주요 실패 재현을 경제사 저장/Undo와 Fed 순수 계산 테스트에 넣고, 지도에는 데이터 참조 검사와 주요 화면 동작 검사를 둔다. 타입 검사에 api·운영 수집 스크립트를 포함할지도 정리한다. 기존 GitHub Actions 수집 검증과 프런트 회귀 검증은 역할이 다르다.

보류 기능은 이 점검만으로 삭제할 이유가 없다. 현재 페이지 지연 로딩과 DB 테이블 분리가 있어 메인 기능과 어느 정도 분리되어 있다. 다만 `server/storage.ts`가 기존 종목 집계와 공통 DB 연결을 함께 소유하므로, 향후 보류 기능 정리 시에는 DB 연결을 먼저 공통 파일로 분리하는 편이 안전하다.

추가 데이터 정리 항목: 영토 분쟁 데이터의 대만 `linked_conflict_id: 13243_none`은 현재 분쟁 목록에 없는 참조였다. 의도한 ‘연결 없음’ 표식이라면 null로 표현하고, 실제 연결 의도라면 ID를 정리할 수 있다. 나머지 이번에 검사한 항로 경유지·발전소/DC 연결·ID 중복과 경제사 시계열 정렬에서는 이상을 발견하지 못했다.

이번 점검은 코드·로컬 빌드·합성 데이터와 브라우저 재현에 근거한다. 실제 Supabase 내용의 무결성, 배포 환경 변수, 외부 API 정상 여부, 최신 데이터의 사실관계, 대량 운영 데이터에서의 장시간 성능은 확인하지 않았다. 운영 코드의 수정·수집·배포는 수행하지 않았다.
